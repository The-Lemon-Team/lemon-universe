# Архитектура Angular-компонентов: SOLID, внешние шаблоны и лимиты размера

Настоящий стандарт обязателен для всех существующих и создаваемых компонентов в проекте Lemon Actions (включая Core Dashboard, Lemon Code Lab, Lemon Home Tracker, Neuron Arena, Timelines и Party Game).

Цель стандарта — предотвратить разрастание компонентов до статуса «God-объектов» (встречающихся в проекте файлов на 2000–4400+ строк), гарантировать читаемость, лёгкость тестирования, изолированность логики и высокое качество кодовой базы.

---

## 1. Обязательное использование внешних шаблонов (External Templates)

### 1.1. Строгое правило `templateUrl`
* **Все Angular-компоненты обязаны использовать внешний файл шаблона**:
  ```typescript
  @Component({
    selector: 'app-example',
    standalone: true,
    imports: [...],
    templateUrl: './example.component.html',
    styleUrl: './example.component.scss', // если требуются локальные стили
    changeDetection: ChangeDetectionStrategy.OnPush,
  })
  export class ExampleComponent { ... }
  ```
* **Запрет на `template: \`...\``**:
  * Категорически запрещено использовать `inline template` для компонентов, содержащих разметку объёмом более **15 строк**.
  * Инлайн-шаблоны допускаются **только** для тривиальных служебных микро-обёрток (например, контейнер с единственным тегом `<ng-content />` или индикатор загрузки из 2–3 тегов).

### 1.2. Почему это критично
1. **Чистое разделение (Separation of Concerns)**: верстка и логика не конкурируют за внимание разработчика в одном файле.
2. **Инструментарий IDE и экосистемы**: внешние `.html` файлы получают полноценную подсветку, поддержку Emmet, автодополнение Tailwind CSS, валидацию шаблонов и проверку доступности (a11y).
3. **Мгновенное сокращение файлов `.ts`**: в крупных компонентах проекта инлайн-шаблоны занимали до 60–75% всего объёма (до 2400 строк HTML внутри TypeScript-файла).
4. **Чистый Git Diff**: изменения разметки не смешиваются с изменениями бизнес-логики и методами класса.

## 2. Лимиты по объёму кода (Line Count Limits)

Для поддержания управляемого размера компонентов устанавливаются строгие лимиты строк кода:

| Тип файла | Рекомендуемый объём | Порог предупреждения (Soft Limit) | Жёсткий лимит (Hard Limit) |
| :--- | :--- | :--- | :--- |
| **Логика компонента (`.component.ts`)** | **50 – 200 строк** | **250 строк** | **350 строк** |
| **Шаблон (`.component.html`)** | **30 – 150 строк** | **200 строк** | **300 строк** |
| **Стили компонента (`.component.scss`)** | **0 – 50 строк** (преимущественно Tailwind) | **80 строк** | **120 строк** |

### Действия при превышении лимитов:
* **Если `.ts` приближается к 250–300 строкам**:
  1. Вынести состояние и координацию в локальный/фичевой сервис (`*Store`, `*Service` или `*State`).
  2. Вынести чистые математические функции, мапперы и форматирование в `.helpers.ts` или `.utils.ts`.
  3. Вынести повторяющиеся преобразования в чистые пайпы (`Pipe`).
* **Если `.html` приближается к 200–250 строкам**:
  1. Разбить шаблон на логические дочерние компоненты (шапка/тулбар, сайдбар, панель фильтров, карточка элемента списка, футер действий).
  2. Изолировать встроенные модальные диалоги и поповеры в отдельные компоненты.

## 3. Соблюдение принципов SOLID

Каждый компонент должен следовать принципам объектно-ориентированного и компонентного дизайна:

### 3.1. S — Single Responsibility Principle (Единственная ответственность)
* Компонент отвечает **исключительно** за представление своего UI-слоя и обработку пользовательских событий (клики, ввод, переключение вкладок).
* **Что НЕ должен делать компонент**:
  * Напрямую выполнять HTTP-запросы и управлять низкоуровневым кэшированием (делегировать в `ApiService` / фичевой сервис).
  * Управлять WebSocket-соединениями и сложными подписками реального времени (делегировать в профильный realtime-сервис).
  * Воспроизводить звуки, обрабатывать сложные аудио-сценарии (делегировать в `SoundService`).
  * Содержать тяжелые алгоритмы фильтрации, сортировки, матричных трансформаций графов или деревьев (делегировать в чистые функции-утилиты или адаптеры).
  * Содержать логику модальных окон других фичей.

### 3.2. O — Open/Closed Principle (Открытость к расширению, закрытость к изменению)
* Компоненты расширяются через:
  * Проекцию контента: `<ng-content select="[header]">`, `<ng-content select="[actions]">`.
  * Кастомизацию через шаблоны: `[templateRef]="customItemTpl"`.
  * Директивы поведения (например, `appModalOverlay`, `appAutoFocus`).
* **Антипаттерн**: добавление в один компонент десятка boolean-флагов (`isTimelineView`, `isPartyMode`, `isHeroCard`, `compactMode`, `embeddedMode`), порождающих ветвления `@if / else` на сотни строк. Вместо этого создавайте специализированные компоненты или используйте композицию.

### 3.3. L — Liskov Substitution Principle (Принцип подстановки Лисков)
* Взаимозаменяемые дочерние компоненты или адаптеры отображения должны следовать единому контракту:
  * Единая сигнатура входных и выходных сигналов (`input()`, `output()`).
  * Предсказуемое поведение при передаче пустых или граничных данных (`null`, `undefined`, пустой массив).

### 3.4. I — Interface Segregation Principle (Разделение интерфейсов)
* Компонент должен принимать только те данные, которые ему действительно нужны для отображения:
  ```typescript
  // ❌ ПЛОХО: передача гигантского доменного объекта на 80 полей
  @Input({ required: true }) fullTimelineModel!: HugeTimelineAggregatedDto;

  // ✅ ХОРОШО: узкий интерфейс или примитивы
  readonly cardId = input.required<string>();
  readonly title = input.required<string>();
  readonly status = input<FlowStatus>('idle');
  ```
* Создавайте специализированные легковесные `ViewModel` или DTO интерфейсы под конкретный виджет.

### 3.5. D — Dependency Inversion Principle (Инверсия зависимостей)
* Зависимости поставляются исключительно через Angular Dependency Injection:
  * Использовать современный `inject(...)`.
  * Запрещено инстанциировать сервисы, мапперы с состоянием или адаптеры через оператор `new` внутри методов компонента.
  * Если компонент переиспользуемый — инжектить абстрактные токены конфигурации (`InjectionToken`), а не конкретные тяжёлые реализации.

## 4. Паттерн Smart (Container) и Presentational (Dumb)

Для структурирования экранов строго применяется разделение на два типа компонентов:

### 4.1. Smart / Container (Контейнеры)
* Привязаны к роутингу или конкретной бизнес-фиче.
* Инжектят сервисы, читают URL-параметры, работают со Signal Store / Facade Service.
* **Главное правило**: Шаблон умного компонента должен быть кратким (обычно до 100 строк) и состоять из композиции дочерних презентационных компонентов.
* Пример разметки контейнера:
  ```html
  <div class="h-full flex flex-col">
    <app-party-hud [roomStatus]="roomStatus()" (action)="handleHudAction($event)" />
    
    <div class="flex-1 grid grid-cols-1 lg:grid-cols-4 gap-4 p-4 overflow-hidden">
      <app-party-sidebar class="lg:col-span-1" [members]="members()" />
      <app-party-canvas class="lg:col-span-3" [timeline]="activeTimeline()" />
    </div>

    @if (openedModal(); as modal) {
      <app-party-modal-host [modal]="modal" (dismiss)="closeModal()" />
    }
  </div>
  ```

### 4.2. Presentational / Dumb (Презентационные)
* Не имеют побочных эффектов и зависимостей от глобальных сервисов.
* Общаются с внешним миром только через:
  * `input()` / `input.required()` — для получения данных.
  * `output()` — для эмита событий наверх.
* Максимально простые шаблоны, OnPush стратегия, легко покрываются Unit-тестами.

## 5. Стандарты Angular для новых и рефакторимых компонентов

1. **Standalone Components**: Все новые компоненты создаются как `standalone: true`.
2. **OnPush Change Detection**: Обязательно указывать `changeDetection: ChangeDetectionStrategy.OnPush`.
3. **Современные Angular Signals**:
   * Для входных параметров использовать `input()` / `input.required()`.
   * Для исходящих событий использовать `output<T>()`.
   * Для производного состояния использовать `computed()`.
   * Для локального мутабельного состояния — `signal()`.
4. **Свежий синтаксис Control Flow**:
   * Использовать `@if`, `@else`, `@for (item of items; track item.id)`, `@switch`.
   * Запрещено использовать устаревшие `*ngIf`, `*ngFor`, `*ngSwitch` в новом коде.
5. **Поддержка модальных окон**:
   * Любые модальные компоненты обязаны отвечать стандарту [`.agents/rules/modal-interaction.md`](./modal-interaction.md).

## 6. Чек-лист проверки компонента (Review Checklist)

Перед завершением создания или модификации компонента сверьтесь со списком:
- [ ] Шаблон вынесен в отдельный файл `*.component.html` через `templateUrl`?
- [ ] Объём `.ts` файла не превышает 250–300 строк?
- [ ] Объём `.html` файла не превышает 200–250 строк?
- [ ] Соблюдён принцип единственной ответственности (Single Responsibility): логика работы с сетью, звуками и данными вынесена в сервисы/хелперы?
- [ ] Установлена стратегия `ChangeDetectionStrategy.OnPush`?
- [ ] Входные/выходные параметры используют сигналы (`input()`, `output()`)?
- [ ] В шаблоне применён современный Control Flow (`@if`, `@for ... track`)?
- [ ] Если в компоненте есть модальное окно — подключена ли директива `ModalOverlayDirective` и соблюдено ли правило `modal-interaction.md`?
